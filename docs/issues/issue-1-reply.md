感谢反馈，诊断报告我逐节看过了，先说结论：**模块本身在这台四代上是正常工作的，10W 更像是平台的充电策略，而不是模块没生效。**

## 一、报告里模块的所有检查点都是通过的

| 检查项 | 报告结果 | 判读 |
|---|---|---|
| 温区伪装 | 11/11 命中，`fast-chg-therm`/`usb*`/`batt-pack-therm` 等 `temp` 均为伪装值、`mode=disabled` | ✅ 生效且稳定 |
| 单实例 | 只有 1 个 `service.sh` 进程 | ✅ 无重复实例抢写 |
| `emul_temp` 写回 | 写入即回读成功 | ✅ SELinux 未拦截 |
| CCL | 13A = `charge_control_limit_max` 满值 | ✅ 没有任何 CCL 限流 |
| 冷却设备 | battery cooling device `cur_state=0` | ✅ 未触发温控限流 |
| 电池温度 | 约 32.9 °C | ✅ 远低于 JEITA 阈值 |

也就是说：**温控该绕的绕了、该伪装的伪装了、限流该解的都解了**，模块这边已经没有可再优化的点了。

## 二、为什么还是 10W

报告里协议是 `PD_PPS`，电池侧实测约 `3.952V × 2.69A ≈ 10.6W`。

- 这台平台的 **PD/PPS 输入电流节点不向用户空间暴露**（大电流走电荷泵，`usb/current_now` 恒为 0，IIO 的 `in_current_*_iin_input` 在本平台返回的是噪声值），所以报告里看不到真实输入功率，**只能以电池功率为准**。
- 在「CCL 满值 + 温度正常 + 无冷却限流 + 温区已绕过」的前提下电池仍只有 10W，说明瓶颈在**模块管不到的地方**。

## 三、请按这个顺序做个 A/B（每次只改一个变量，尽量保持电量/温度接近）

1. **确认是不是模块的副作用**：`config.prop` 里 `ENABLE_THERMAL_BYPASS=0` → 重启 → 同电量同温度再充。
   - 功率回到 40W+ → 确实是模块副作用，进第 2 步；
   - **仍然是 10W** → 与模块无关，直接看第 4 步。
2. **[V7.0 新增] `ZONE_MODE=2`** → 重启：只伪装温度、**不禁用温区**。
   部分平台在温区被 `disabled` 后会回落到保护性小电流（约 10W），这个模式可以绕开该逻辑。
3. **[V7.0 新增] `KILL_THERMAL=1`** → 重启：开启「周期击杀温控进程」（默认是 0 不杀）。
   ⚠️ 顺便说明：我在 V7.0 排查时发现，**V6.x 的「杀温控进程」其实一直是失效的**——
   它用 `ps -A -o PID,NAME` 匹配进程名，而模块运行环境里 `ps` 列不出别的进程名（实测命中数恒为 0），
   所以 V6.x 实际从没杀过任何进程。V7.0 改用 `/proc` 扫描后才真正生效，因此默认改回 `0`，
   避免升级后行为被悄悄改变。这一项现在是「可选激进项」，想试可以打开看是否有变化。
4. 若上面都无效，重点怀疑**充电器 / 线材 / 接口**：
   - 原装 68W 头 + **原装 C-to-C 线**、插紧、换个口/换一面；线材老化或非 C-to-C 时会掉到 5V/2A 这档；
   - 低电量时才锁 10W 的话，也留意是不是**边充边用/亮屏重载**导致平台主动压流。
